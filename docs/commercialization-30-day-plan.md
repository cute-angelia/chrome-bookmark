# CutBookmark 商业化 30 天执行计划

编制日期：2026-11-05。建议执行日期：2026-11-06 至 2026-12-05，时区为 Asia/Shanghai。若实际启动时间不同，按 Day 1 至 Day 30 整体顺延，保留各阶段依赖。

## 一、执行前提与本月目标

### 1. 这份计划解决什么问题

本月不追求做出完整商业平台，而是回答三个问题：谁会持续使用 CutBookmark，什么功能值得付费，能否重复找到这样的用户。

默认由你一人执行，每天投入 2–4 小时，表内总投入 87.5 小时；开发日需要连续时间。每个时间预算已包含约 20 分钟的用户回复和记录。若只能投入 1 小时，不压缩验证步骤，将周期延长至 60–90 天。

本计划是待执行的工作表，不代表访谈、开发、上架或收款已经完成。文中的人数、转化率和价格均为内部验证假设，不是行业标准、统计结论或收入承诺。

### 2. 基于现有产品，而不是重新做一个产品

| 当前能力或限制 | 本月怎么处理 |
| --- | --- |
| 已有 Chrome 原生书签整合、可视区域截图、标签、笔记、搜索和三栏工作台 | 作为免费试用底座，不重写架构 |
| 已有本地 IndexedDB、手动备份和恢复 | 优先验证数据可靠性，保留用户导出权利 |
| 已有远程服务连接能力 | 作为可选连接，不包装成已成熟的官方云同步 |
| 目前截图不是完整网页归档 | 不宣传全页保存、完整离线阅读或永久网页归档 |
| 暂未在当前代码中发现完整商业会员和计费体系 | 先小规模人工交付或使用现成授权能力，不先开发完整账户平台 |
| 弹窗与工作台的目录操作存在需要核对的交互细节 | 用真实任务走查；只处理阻断试用的具体问题 |
| 尚无本轮真实用户及付费数据 | 从访谈、试用和真实报价开始，不预设需求已成立 |

### 3. 优先用户与场景

首批用户：最近一个月实际做过网页竞品研究的 UI/UX 设计师，或独立产品开发者。先分别访谈，再在 Day 7 选择更容易触达、痛点更明确的一组作为主客群。

核心场景：用户收集 SaaS 定价页、注册流程、落地页和交互案例，数天后为自己的方案找回资料并复用。

对外暂用一句话描述：**把网页案例、截图和研究笔记放在一起，做方案时找得回来。**

不以“支持三栏”“AI 第二大脑”“全能知识库”作为购买理由。最终文案要随着访谈证据调整。

### 4. Day 30 目标

| 指标 | 本月目标 | 怎样才算完成 |
| --- | --- | --- |
| 定向邀请 | 40–60 位独立潜在用户 | 符合客群条件，逐人记录，重复触达不重复计数 |
| 用户访谈 | 15 次 | 每次约 20 分钟，留下真实任务、替代方案和原话记录 |
| 真实安装 | 20 人 | 在自己的浏览器成功安装并完成首次保存，不是只下载了安装包 |
| 激活用户 | 15 人 | 首周保存至少 5 条资料，并找回打开至少 1 条此前保存的资料 |
| 自发复用 | 至少 5 人 | 在不同日期、无当日提醒的情况下，为真实工作使用旧资料 |
| 专业功能试用 | 5–8 人 | 用自己的真实任务试用，不只是看演示 |
| 明确报价 | 5–8 人，争取 8 人 | 完成专业试用，看过具体已交付功能、价格与权益后作出回应 |
| 真实付费 | 争取 3–5 人 | 非人情支持单，已付款、交付并核对到账；退款另记 |
| 商业结论 | 1 份 | 明确继续、调整或暂停，以及支撑决定的证据 |

3–5 笔付费只是早期信号，不足以证明产品市场匹配。若拿不到付费，也要区分问题出在需求、功能、价格、安装还是支付条件，而不是笼统认定产品失败。

### 5. 本月不做清单

- 不做移动端、团队权限、企业私有化和完整云同步。
- 不同时开发 OCR、AI 摘要、语义搜索、批量截图和协作功能。
- 不因某一位用户愿意付钱就接入偏离主场景的定制需求。
- 不购买泛流量、不购买评价、不做返现换好评。
- 不把用户截图、网址、笔记默认上传给分析或 AI 服务。
- 不为了收费收回已有基础收藏和数据导出能力。

## 三、第 1 阶段：确认问题和可交付底座

### Day 1：冻结假设，建立执行记录

**怎么做**

1. 写一张目标卡：首批用户是谁、最近一次什么工作会用到产品、现在用什么替代、为什么可能付 ¥129。
2. 建立一张表，按本文第八节的字段记录潜在用户、访谈、安装、激活、复用和付费。先手工记录，不开发数据后台。
3. 从自己的联系人、设计师社群、独立开发者社区整理 20 位候选人，各客群先约一半；只记录有正当渠道获得的联系方式。
4. 给当天设定固定工作时段，并预约 Day 3、Day 4 的访谈。工作记录中把“观察到的事实”和“自己的解释”分开写。

**当日产出**：1 张目标卡、1 张追踪表、20 人候选名单。

**完成标准**：每位候选人都有“为什么符合客群”的依据，而不只是“可能对工具感兴趣”。

**未达标时**：先缩小到“最近一个月做过 SaaS 网页研究的人”，不要扩大成所有浏览器用户。

### Day 2：用自己的真实任务验收底座

**怎么做**

1. 使用独立 Chrome 测试配置和可丢弃的书签数据，准备 10 个公开网页案例，避免在主浏览器里测试删除和恢复。
2. 按“保存截图、选择目录、添加标签与笔记、关闭重开、搜索找回、打开原页”的顺序操作，记录耗时和失败位置。
3. 导出备份，在隔离环境中恢复并核对链接、目录、截图、注解。核实恢复操作会覆盖什么，不把未经验证的恢复能力写进宣传。
4. 测试未配置远程服务、截图失败和不能截图的页面是否有清晰反馈。检查弹窗目录与实际保存结果是否一致。

**当日产出**：验收表，以及最多 3 个必须解决的试用阻断问题。

**完成标准**：本地核心任务能走通；没有已知的数据丢失、误删或保存到错误位置的问题。

**未达标时**：先停止招募安装，只做访谈。可靠性不过关时不引入付费功能。

### Day 3：开始第一轮访谈

**怎么做**

1. 使用第九节的邀请模板，给 10 位候选人分别发送消息；每条写明为什么找他，不群发相同广告。
2. 完成 2 次约 20 分钟访谈。前 15 分钟不展示产品，询问最近一次收集和找回案例的具体过程。
3. 让对方自愿展示不敏感的任务过程，记录收藏位置、检索方式、找不到时的补救办法。
4. 最后展示 1 分钟产品，问“你会在哪个实际任务里试一下”，而不是问“是不是很棒”。

**当日产出**：2 份访谈记录，累计 10 人定向邀请。

**完成标准**：每次访谈至少得到一个真实事件，不能只有抽象评价。

**未达标时**：若无人回复，先换成认识的目标用户或请联系人引荐，不把沉默解释成需求不存在。

### Day 4：识别反复发生的资料复用问题

**怎么做**

1. 再完成 3 次访谈，使累计达到 5 次，尽量包含两个初始客群。
2. 把痛点分成“收藏困难、整理费时、找不回来、无法用于交付、跨设备缺失”，每条保留来源用户编号。
3. 记录现有替代工具、使用频率、是否付费、迁移顾虑。不要主动要求用户搬迁全部旧资料。
4. 问最近一次问题导致了什么损失，例如重找了多久、重复截图、方案遗漏，但不替用户估算收益。

**当日产出**：累计 5 份访谈、带用户证据的痛点表。

**完成标准**：能够指出至少 2 位独立用户描述的同一类问题。

**未达标时**：保留两种假设继续访谈，不因为一个强烈意见就确定功能。

### Day 5：处理阻断问题，录制演示

**怎么做**

1. 只处理 Day 2 中影响核心路径的最多 2 个问题，优先顺序为数据可靠性、保存正确性、安装和任务理解。
2. 代码有改动时执行本次改动相关测试，再执行 `npm run build`，用新的 `dist/` 在扩展中验收，记录版本和结果。
3. 用自己的公开网页案例录制 60 秒演示：保存案例、加一句研究笔记、切换到已有资料、检索并打开。
4. 删掉没有实际帮助的演示介绍。明确展示的是可视区域截图，不制作用户尚未具备的功能效果。

**当日产出**：一份可复现的演示构建、一个 60 秒视频、已知限制清单。

**完成标准**：第三方看完能够说清楚产品解决什么任务，核心功能与演示一致。

**未达标时**：问题无法在当天解决，就延后分发；访谈继续，不通过包装掩盖故障。

### Day 6：准备试用入口与分发材料

**怎么做**

1. 用现有网站、简单公开说明页或表单建立唯一入口，包含一句定位、演示、适用人群、真实限制、试用申请和联系渠道。
2. 表单只收集联系方式、职业和最近的使用场景；不要求上传完整书签库、截图或浏览记录。
3. 准备安装和卸载说明。商店可用时优先商店；私测包只面向明确同意开发者模式安装的用户，并说明更新步骤。
4. 准备隐私说明与商店材料，核对截图何时采集、数据存放在哪里、远程服务何时接收数据、权限为什么需要。

**当日产出**：1 个可打开的试用入口、安装说明、隐私说明草稿、商店材料清单。

**完成标准**：入口中没有未实现的云同步、AI、完整网页归档或绝对安全承诺。

**未达标时**：不先做精美官网；一页清楚、准确的说明优先于品牌装修。

### Day 7：第一次决策复盘

**怎么做**

1. 再完成 3 次访谈，累计达到 8 次；汇总真实问题的频次和具体程度。
2. 在两个初始客群中选择一组作为后续招募主客群，理由必须包含可触达性和实际任务证据。
3. 检查是否至少 3 人描述过相近问题，至少 2 人愿意带着近期真实任务试用。
4. 写下“继续验证什么”和“暂不做什么”，更新入口文案，但不新增大功能。

**当日产出**：一页周复盘、确定的主客群、下一批邀请名单。

**完成标准**：能用真实案例解释为什么选择这组人，而不是因为他们点赞最多。

**未达标时**：第二周优先补足访谈，不强行进入专业功能开发。

## 四、第 2 阶段：让真实用户完成第一次复用

### Day 8：落实商店和私测两条分发路径

**怎么做**

1. 检查商店开发者账户、所需材料、隐私披露、功能说明和付款功能标注是否准备充分。
2. 条件齐备就提交；若尚有数据或权限问题，先修正再提交，不以本计划日期强行上线。
3. 商店审核期间，向愿意参与私测的用户提供构建包、版本号和安装指南；不要引导用户绕过组织安全管理。
4. 从未参与开发的人中找 1 人测试安装说明，观察是否能在 5 分钟内完成。分别记录商店安装和私测安装的摩擦。

**当日产出**：提交或未提交的具体状态、私测分发包、安装过程记录。

**完成标准**：至少有一条适合目标用户、可以实际执行的安装路径。审核通过日期不在承诺范围内。

**未达标时**：仅保留访谈和演示，不把“无法安装的人”算作激活失败或专业功能无需求。

### Day 9：提前确认如何收款和交付

**怎么做**

1. 暂定单一测试价格 ¥129，明确这是假设价格，不同时跑多个价格组。
2. 草拟权益：已交付的专业功能、当前大版本永久使用、12 个月更新、支持渠道、不包含云服务和无限 AI。
3. 核对你可合法开通的收款方式、商户资格、退款能力、到账和手续费、凭证要求；以服务商当前规则和实际开通结果为准。
4. 明确前 10 单如何交付。可采用受邀内测的人工版本交付，或已可用的授权服务；不为这 10 单先开发完整会员系统。写清安装、更新和退款后的权益处理。

**当日产出**：一页报价与权益草稿、支付开通状态、人工交付流程。

**完成标准**：知道如何核实到账、交付可用产品和处理退款。面向公开用户收费前必须有真实可用的路径。

**未达标时**：改为记录购买意向，不收款、不把承诺购买计入收入。收款不是用户截图或笔记上传的理由。

### Day 10：观察首批 3 人上手

**怎么做**

1. 预约 3 位目标用户，每人 20–30 分钟，优先选择有近期工作任务的人。
2. 请他们独立安装、保存 3 条自己的案例、加笔记并找到其中一条。除非卡住，否则不解释应该点哪里。
3. 记录首次成功时间、操作误解和主动求助次数；愿意让你看屏幕不代表同意你保存内容。
4. 约定接下来两天在工作中再保存几条资料，不要求每天签到，也不承诺奖励评价。

**当日产出**：3 份上手观察、首次成功耗时、最多 3 个主要摩擦点。

**完成标准**：至少 2 人能完成核心任务；陪同完成的检索只算引导任务，不算自发复用。

**未达标时**：将后续开发时间优先用于上手阻断，而不是增加收费理由。

### Day 11：减少解释后再观察一批用户

**怎么做**

1. 针对 Day 10 最明显的 1 个阻断修改说明或产品；代码改动仍需相关测试和构建。
2. 邀请另外 3 人按同一任务操作，用一致方式记录，不为不同用户临时讲解不同流程。
3. 再完成 2 次问题访谈，累计向 10 次推进，补足尚不清楚的替代方案和迁移顾虑。
4. 若有人当天主动回来使用旧资料，记录时间和目的；把客服提醒后的使用单独标注。

**当日产出**：累计约 6 人安装、前后两批上手差异、累计约 10 次访谈。

**完成标准**：解释成本下降，或至少明确阻断来自安装、产品还是任务本身。

**未达标时**：不要一次重做整个界面；只处理能够对应到观察记录的问题。

### Day 12：建立可追踪的首批试用队列

**怎么做**

1. 再邀请约 4 人安装，使累计约 10 人。逐一记录首次成功使用日期，不把发送安装包当作安装。
2. 回访 Day 10–11 用户，询问是否在真实工作中保存和找回资料；优先看结果，不提示他们完成指标。
3. 标记已激活、尚未激活和不能判断三种状态，不能判断的数据不填成零。
4. 请愿意继续试用的人选择一个 7 天内需要完成的研究任务，供后续复用回访使用。

**当日产出**：首批试用队列表、激活日期、每人的真实任务。

**完成标准**：能够区分“装上了”“完成引导了”“真的在工作里用了”。

**未达标时**：先让已有用户走通，不用继续加人掩盖激活问题。

### Day 13：用任务而不是想象选择收费方向

**怎么做**

1. 补足约 5 次访谈，使累计目标达到 15 次，未达到就如实保留缺口。
2. 向合适用户展示两个清楚标注为概念的方案：截图文字搜索，以及项目资料导出。
3. 每人先描述自己的待办任务，再说哪个方案能帮助完成；询问能否提供不敏感的样例并预约测试。
4. 对有具体任务的人说明“假设该功能可用，测试价为 ¥129”，记录拒绝理由和愿意采取的下一步。此时不收未交付功能的钱。

**当日产出**：功能需求证据表、概念反馈、带价格的意向记录。

**完成标准**：至少 3 人为同一功能提供独立真实任务，其中至少 2 人愿意预约试用。

**未达标时**：不把“两个都挺好”当作开发证据；继续核实问题。

### Day 14：决定是否投入专业功能开发

**怎么做**

1. 汇总邀请、访谈、安装、激活和旧资料复用，逐项检查分母和证据来源。
2. 进入开发的最低条件暂定为：至少 10 人安装、5 人激活、3 人提出相近专业任务、2 人愿意参与试用。
3. 满足条件，选择一个功能；两者证据接近时优先实现成本较低的项目资料导出，不默认押注 OCR。
4. 不满足条件，就把 Day 15–20 改成补访谈、修复上手和观察复用。保留后半月复盘日期，不为了完成日历而收费。

**当日产出**：带证据的“开发 / 继续验证”决定。

**完成标准**：决定同时考虑需求证据、实现成本和当前数据可靠性。

**未达标时**：不进入开发分支；本计划允许当月得到“还不值得收费”的结论。

## 五、第 3 阶段：交付一个有证据的专业功能

以下 Day 15–21 为进入开发分支的安排。若 Day 14 未通过门槛，每天把开发时间替换为 1–2 次访谈、1 次试用观察和 1 个已证实阻断的处理。

### Day 15：冻结功能边界和验收任务

**怎么做**

1. 从第七节选择一个最小范围，写明用户输入、完成结果、失败反馈以及明确不支持的内容。
2. 请 2 位提供需求的人确认这个范围是否解决其任务，并提供非敏感验收样例。
3. 设定交付预算为 Day 16–20 的现有开发时段，不同时扩展其他专业功能。
4. 根据实际范围更新 ¥129 权益说明，不写“未来会加入的所有功能”；保留测试未通过时不收费的条件。

**当日产出**：一页功能范围、至少 2 个用户任务样例、更新后的报价说明。

**完成标准**：可以明确判断做完还是没做完，而不是泛泛地“提升搜索体验”。

**未达标时**：范围继续缩小，不以“开发时再看”为验收依据。

### Day 16：先做技术验证，不先做完整界面

**怎么做**

1. 用 2–3 小时验证最难的环节：OCR 的本地运行与扩展兼容性，或导出内容和图片的可靠打包。
2. 用 Day 15 的样例运行，观察准确性、耗时、离线限制及是否需要新增权限或外部服务。
3. 不用随机数据代替真实截图验收，也不把需要云端处理的方案宣传为完全本地。
4. 若核心难点当日无法证明可行，停止该路线；只有备选方案也有需求证据才切换，否则返回验证，不临时转做 AI 摘要。

**当日产出**：可运行小样、已知限制、继续或降级决定。

**完成标准**：在目标扩展环境里运行过，不只是独立脚本成功。

**未达标时**：不延长为无期限技术攻关，更新试用者预期并取消不可靠的交付日期。

### Day 17：完成核心任务

**怎么做**

1. 在现有数据和目录结构上实现最短路径，不引入账户、协作或新的同步协议。
2. OCR 分支先完成“选择已有截图、识别文字、保存结果、关键词找到来源”；导出分支先完成“选目录、导出文件、离线查看”。
3. 保留原数据，新增内容不覆盖截图、原笔记或来源书签；避免为付费功能改变原生书签行为。
4. 对本次新增的数据边界或输出添加相应测试，执行相关验证与构建。

**当日产出**：核心任务可操作的构建，以及相关验证记录。

**完成标准**：使用验收样例可完成任务，失败时不会破坏原资料。

**未达标时**：继续删减范围，不用界面装修代替核心结果。

### Day 18：让用户能独立完成操作

**怎么做**

1. 将功能入口接入现有工作台的合适位置，保留已形成的界面和术语，不额外塞入营销横幅。
2. 增加必要的开始、进行中、成功、无结果和失败反馈；耗时任务避免让用户误以为产品卡死。
3. 请 1 位试用者在不被指导的情况下完成样例，记录不理解的地方。
4. 修复最明显的理解问题，执行涉及范围的测试与 `npm run build`，再从扩展验证。

**当日产出**：集成版本、用户独立操作记录、剩余缺陷表。

**完成标准**：用户不需要听开发原理，就能判断怎么开始、是否完成、结果在哪里。

**未达标时**：优先修正操作路径，不靠增加长篇解释文字补救。

### Day 19：验证质量，观察第一批用户是否回来

**怎么做**

1. 逐项运行 Day 15 的验收样例，并验证当前改动涉及的保存、搜索、导出或数据读写行为。
2. 再走一次相关核心回归路径，执行构建并核对 `dist/`；只记录实际运行的测试，不宣称全量通过。
3. 回看 Day 10–12 安装队列，分别观察每人首次使用后第 7–9 天是否为工作复用了旧资料。当天未成熟的用户暂不计算。
4. 回访时先问这几天做了什么、资料用在哪里；把回访后才发生的操作标成“提醒后使用”。

**当日产出**：验收结果、已知限制、首批 D7 复用记录。

**完成标准**：专业功能没有核心阻断，复用记录可区分自发、提醒后和仅陪同演示。

**未达标时**：仍可邀请免费验证，但不能把存在核心缺陷的功能作为成熟商品销售。

### Day 20：专业功能试用和交付演练

**怎么做**

1. 向 5–8 位具有对应真实任务的用户发出试用邀请，写清版本、限制、反馈方式和试用期。
2. 默认从个人实际拿到可用版本当天起给 7 天体验。若交付延迟，体验结束和报价时间顺延，不压缩用户体验期。
3. 用自己的测试身份走通获取版本、安装、确认权益、更新和联系支持的流程。
4. 对支付方式进行服务商支持的测试或小额闭环验证，并核对退款过程；测试订单不计入商业成交。

**当日产出**：专业功能试用名单、每人开始和到期日期、交付及支付检查结果。

**完成标准**：已有用户实际拿到能运行的功能；支付可用与否有明确记录。

**未达标时**：未交付者不开始计时；支付不可用则仅验证意向，不收款。

### Day 21：决定能不能进入收费阶段

**怎么做**

1. 检查至少 2 位专业试用者是否完成过真实任务，而不只是浏览新功能。
2. 复核核心缺陷、权益说明、支持和退款路径，任一关键项缺失就不启动收费。
3. 结合首批复用，判断付费功能是在帮助已存在的工作流程，还是仅仅制造短期新鲜感。
4. 写下接下来一周的销售对象名单、沟通时机与不适用用户；不向不符合条件的人广泛推销。

**当日产出**：进入收费 / 延长试用 / 返回问题验证的决定。

**完成标准**：至少有真实使用结果且可以完成交付和售后，不以“功能终于写完了”作为收费理由。

**未达标时**：继续完成验证；首月零收入也必须如实记录。

## 六、第 4 阶段：获取第一批订单并决定是否继续

### Day 22：发布一篇具体工作案例

**怎么做**

1. 只选一个你能接触到目标用户的渠道，不同时运营多个平台。
2. 以自己的真实案例写“如何收集并找回一组定价页参考”，展示输入、操作和最终用于什么工作。
3. 如果使用用户案例，先取得明确许可并去除敏感信息；没有许可就全部用自己的资料。
4. 结尾只保留一个动作：申请试用。通过独立入口参数或表单来源字段记录渠道，不向用户收集浏览内容。

**当日产出**：一篇案例、一个入口、渠道来源记录。

**完成标准**：内容展示实际结果，没有虚构客户、收益、评价或已实现功能。

**未达标时**：继续一对一邀请，不把发帖数量当成获客成果。

### Day 23：扩展精准试用，分清拒绝原因

**怎么做**

1. 回复案例带来的询问，优先邀请符合主客群且有近期任务的人；不足时补充少量定向邀请。
2. 向累计 20 人真实安装推进，但不为达人数接入无关人群。
3. 对没有安装或不愿继续的人，只问一个主要原因：不需要、已有替代、安装顾虑、隐私、体验、价格或其他。
4. 有需要时协助一次安装；不持续追催，不把技术帮助后的使用当成自然留存。

**当日产出**：更新的漏斗、渠道来源、拒绝原因表。

**完成标准**：能够判断新的试用者是不是同一类用户，且知道他们在哪里流失。

**未达标时**：不要通过泛化定位换取更多安装数，优先找对人。

### Day 24：核实专业功能是否真的完成工作

**怎么做**

1. 预约至少 3 位专业试用者，观察其完成自己的任务，不再使用开发者准备的标准演示数据。
2. OCR 分支观察是否能用记忆中的文字找到正确截图；导出分支观察结果能否用于其评审、汇报或个人整理。
3. 记录结果、耗时、是否仍需旧工具，以及用户为什么愿意或不愿意继续使用。
4. 只有用户自己给出使用前后的时间或质量差异时才记录，不将演示推导为“效率提高十倍”。

**当日产出**：至少 3 份专业任务结果、购买阻断清单。

**完成标准**：至少 2 人完成真实任务，并能明确说出功能帮助了哪一步。

**未达标时**：停止主动售卖，先修正任务匹配或实现问题。

### Day 25：冻结销售版本和承诺

**怎么做**

1. 只修复 Day 24 证明会阻止使用或购买的最多 2 个问题，不新增功能。
2. 运行相关测试和构建，在扩展中核验最终版本，保留版本号、安装包和已知限制。
3. 完成报价页：功能范围、¥129、版本权益、更新期限、设备或交付限制、支持渠道、退款方式。
4. 本轮可主动提供 14 天退款承诺，但要先确认自己能执行，并说明不能替代适用的法定权利；到 Day 30 尚未结束退款期的订单标为待观察。

**当日产出**：冻结版本、准确报价页、退款和支持说明。

**完成标准**：用户付款前能判断买到什么、不包含什么、出问题找谁。

**未达标时**：延期报价，不以“早鸟特惠”掩盖尚不能交付的状态。

### Day 26：专业试用期末回访，核实较长期复用

**怎么做**

1. 回访 Day 20 开始专业试用的用户，确认是否完成真实任务、是否还有阻断。完整 7 天试用通常在 Day 27 才结束，今天不催提前付款。
2. 确认每人拿到可用版本的实际时间和试用到期时间，准备次日的报价名单。延期交付者的报价继续顺延。
3. 记录功能有用、尚无任务、存在缺陷和不想继续等状态。不要用口头“以后会买”填入成交列。
4. 对早期安装队列观察首次使用后第 14–16 天的真实复用；每人的窗口不同，未到窗口结束先标待观察。

**当日产出**：专业试用期末反馈、D14 复用记录、次日报价名单。

**完成标准**：每位待报价用户的试用状态和实际使用结果清楚，没有人为缩短体验期。

**未达标时**：不要立即降价；先分清功能无价值、尚无任务、交付顾虑和价格不匹配。

### Day 27：正式报价，完成首批订单闭环

**怎么做**

1. 对已经完整体验 7 天、且确实使用过专业功能的用户，使用第九节模板发送相同报价，向累计 5–8 人明确报价推进。
2. 分开记录付款、考虑、拒绝和无法付款，允许直接拒绝。不使用虚假限时，也不临时向个别用户给折扣。
3. 对付款订单核对到账并交付，确认用户能安装和使用；在记录中保留订单编号，不保留支付敏感信息。
4. 如果当天没有订单，先记录主要原因，给对方正常决策时间，不在一天里重复催问。

**当日产出**：首轮购买决定、订单与交付记录、拒绝原因表。

**完成标准**：付款用户拿到可用产品；试用未结束的人保留完整体验期，不为月末目标强行结算。

**未达标时**：如实记录零订单或延迟订单，未交付的款项单独列为待交付，不算成功闭环。

### Day 28：核对漏斗，排除被提醒制造的留存

**怎么做**

1. 对报价后表示考虑的人，至少间隔一天再做最多一次跟进，了解是否缺少信息；对新订单完成到账和交付核对。去重并更新全链路人数。
2. 把 Day 10–12 的成熟队列单独统计，后来的用户不进入其 D7、D14 分母。
3. 区分自发复用、提醒后复用和仅陪同任务；主动核实没有记录的用户，不把无法确认直接当流失。
4. 若要求用户回忆，标注“用户自报”；若有经同意的使用计数，标注其来源，不混同证据强度。

**当日产出**：分母清楚的漏斗和复用表，仍待观察的人数。

**完成标准**：报告保留绝对人数。例如写“成熟队列 8 人中 3 人自发复用”，不只写“37.5% 留存”。

**未达标时**：先补齐口径和记录，再下结论；小样本不做显著性推断。

### Day 29：计算是否值得继续经营

**怎么做**

1. 汇总真实现金支出、开发时数、访谈及获客时数、每单交付支持时间、收入、退款和待交付款。
2. 分别计算现金贡献和包含个人工时的试算，使用第十节公式，不把自己的时间视为免费。
3. 按渠道比较合格试用数、激活数、付费数及投入时间；没有付费的渠道标“本月未验证”，不要除以零。
4. 询问付费用户下个月准备在哪个真实任务中继续使用，不把当前买断销售额称为 MRR。

**当日产出**：单位经济表、渠道效率比较、交付成本问题清单。

**完成标准**：能解释收入来自哪里，以及多卖 10 单会增加多少工作和成本。

**未达标时**：优先缩短交付与支持，不自动转做订阅或企业定制。

### Day 30：决定继续、调整还是暂停

**怎么做**

1. 按第十一节决策表检查需求、复用、付费和可重复获客的证据，不仅看销售额。
2. 写一页结论：实际结果、关键用户原话、主要失败原因、哪些假设被支持、哪些仍不知道。
3. 下个月只安排三项工作，必须对应本月已观察到的约束；为每项写一个验收标准。
4. 给试用者和付费用户发送后续安排，继续履行支持与退款承诺。未结束的退款期或观察窗口，在结论中注明后续核对日期。

**当日产出**：月度商业结论、下阶段三项任务、用户后续通知。

**完成标准**：能够明确作出以下之一：继续同一定位、调整客群或任务、暂停新增开发。不用“再加几个功能看看”代替决定。

**未达标时**：若数据不足，给一个最多两周的补证据计划，并指明缺的是哪项证据，而不是无限延期。

## 七、付费功能只选一个

### 方案 A：项目资料导出

适用证据：用户已经在做研究笔记，并经常手工把截图、网址和判断整理给自己或同事看。

最小范围：选择一个已有目录，导出一个本地 HTML 文件，包含标题、来源链接、已有截图和笔记。截图可内嵌，限定在已验证规模内，优先保证文件离线可打开。输出纯文本字段时正确转义，不执行来源内容。

**明确不做**：在线分享、团队协作、自定义模板系统、直接生成 PPT、批量自动写报告。

| 验收项 | 最低结果 |
| --- | --- |
| 内容完整 | 自有测试数据中，选定目录下的 20 条资料没有遗漏、串项或错误来源 |
| 截图可用 | 有截图正常显示，无截图保留标题和来源，不伪造图片 |
| 中文内容 | 中文标题、笔记、换行和常见符号正常显示 |
| 安全与隐私 | 导出仅由用户主动触发，不上传云端，不把笔记作为脚本执行 |
| 工作结果 | 至少 2 位目标用户能将导出用于自己的真实评审或资料整理 |

### 方案 B：本地截图文字搜索

适用证据：用户经常记得截图中的文字，但标题、标签和笔记无法帮助其找回资料。

最小范围：用户手动选择已有截图进行文字识别，保存提取结果；在现有检索中匹配识别文字并返回来源书签。先验证中英文清晰网页文字，不承诺所有图片都准确。

**明确不做**：语义搜索、相似图片搜索、自动理解设计风格、全库后台扫描、AI 问答、完整网页全文搜索。

| 验收项 | 最低结果 |
| --- | --- |
| 环境兼容 | 在打包后的 MV3 扩展中真实运行，所需代码和识别资源的加载方式经过核对 |
| 找回效果 | 10 张有权使用的清晰测试截图中，预先选定的每图一个目标词至少 8 个能找回正确来源 |
| 真实任务 | 至少 2 位目标用户用自己的非敏感截图完成文字找回任务 |
| 数据保护 | 识别结果不覆盖原笔记和截图；失败不损坏原资料 |
| 处理反馈 | 显示进行中、成功和失败状态；记录目标设备耗时，不编造性能承诺 |
| 隐私披露 | “本地识别”与实际一致；如需下载识别资源，说明首次联网和资源行为 |

## 十、时间、预算与单位经济

### 1. 现金预算上限

建议首月可控现金支出上限为 ¥1,000。这是预算分配，不是服务商价格报价。支出前以真实价格核对，未使用的预算不必花完。

| 项目 | 建议预留 | 使用条件 |
| --- | --- | --- |
| 入口页、域名或已有工具补充 | ¥0–200 | 能用现有工具就不新购 |
| 商店、支付或交付相关开通费用 | ¥0–300 | 先确认资格与实际费用，超过预算先调整 |
| 访谈感谢或必要工具 | ¥0–200 | 不与购买、好评和正向反馈绑定；有激励单独记录 |
| 开发和交付必要支出 | ¥0–200 | 不先购买长期服务器或大量 AI 额度 |
| 机动 | ¥100 | 仅处理阻断 |

开发时间上限：专业功能预算约 20 小时，核心难点在 Day 16 先验证。若必须重构架构才能交付，放弃本月收费目标，重新评估路线。

### 2. 收入与成本怎么记

按 ¥129 测试价，3–5 笔订单的销售额是 ¥387–645，尚未扣除手续费、退款和成本。本月重点是验证交易，而非覆盖全部开发工时。

```text
本月净收款 = 实际到账金额 - 已退款金额
本月现金结果 = 净收款 - 本月实际现金支出

每单可变贡献 = 售价 - 支付手续费 - 单单新增的交付与服务现金成本
现金获客成本 = 对应渠道直接获客支出 / 该渠道有效付费人数
工时获客成本 = 对应渠道招募与销售工时 × 自定时薪 / 该渠道有效付费人数

一次性投入 = 开发、基础材料、初始验证等投入
后续单单工作 = 收款核对、交付、安装支持、售后等
```

渠道没有成交时不计算除法，直接写“投入 X，付费 0，尚未验证”。现金预算为零也不代表获客成本为零，仍要记录工时。

买断订单不产生 MRR。首月不具备长期流失率或终身价值数据，不用推测的 LTV 美化结果。

## 十二、发布与信任底线

1. 隐私说明要与真实数据路径一致，清楚解释截图、本地数据、远程服务和必要权限。Chrome Web Store 对用户数据披露及最小权限有明确要求，提交前按当前政策核对。[Chrome Web Store 官方政策](https://developer.chrome.com/docs/webstore/program-policies/policies)

3. 保留免费核心能力和用户数据导出，不把资料锁在付款墙后。专业收费依靠新增工作价值，而不是制造迁出困难。
4. 商店素材、演示和报价只描述已经可用或清楚标记为概念的能力；不把可视区域截图当作完整网页存档。
5. 所有代码改动都执行相关范围验证和 `npm run build`，用 `dist/` 验收。记录未运行的测试，不为了商业计划修复无关失败。
6. 公开发布前核对来源代码、依赖、图标和演示素材的授权与署名要求；具体商户、税务和退款义务按实际经营地区与服务商要求核实。
